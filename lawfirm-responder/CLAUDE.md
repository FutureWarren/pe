# CLAUDE.md — 律所微信群 AI 第一响应助手

本文件对在本目录（`lawfirm-responder/`）工作的 Claude Code 具有约束力。

## 项目定位

企业微信客户群里的 AI 第一响应屏障：客户消息在人工无法及时回复时，能答的直接答，
不能答的先安抚、承接、并通知人工。核心价值是**消灭冷场**，不是替代客服。
北极星指标：客户消息首次响应时长（中位数）。

## 合规护栏（不可违反）

以下规则硬编码于 `responder/compliance/`，**任何情况下不得绕过、弱化或有条件豁免**：

1. **渠道**：只对接企业微信官方 API。禁止引入任何个人微信协议桥接/逆向方案（封号 + PIPL 风险）。
2. **出口闸门**：所有 AI 生成文本（含影子模式草稿）必须经过 `compliance.guard.guard()`。
   禁止事项命中即丢弃原文、回退安全承接模板。
3. **禁止事项清单**（`compliance/forbidden.py`）：承诺结果、预测本案判决、提及任何费用金额、
   报价/改价、评价对方当事人或司法机关、催促客户做法律行为、冒充律师身份。
4. **免责句式**（`compliance/disclaimer.py`）：机制必须保持可用（verify 按开启态验证），
   但生产 `disclaimer_required` 默认关闭（业务决策 2026-07，暂不落地）。开启前句式须合伙人书面确认，
   AI 不得改写句式本身。
5. **人工优先**：律师近期发言过的群 AI 静默；紧急情形（拘留/传唤/开庭临近/情绪崩溃/投诉）
   只做一句安抚 + 强提醒承办律师，不展开回答。
6. **自指本案一律承接**：消息含「我的案子」等自指时，即使话题通用也不直接作答。
   **例外（2026-08-07，律所方要求，待书面确认）**：首轮咨询窗口
   （`is_kf` + 未成交 + 未转人工 + 客户已把事说出来）不适用本条。
   理由：这条护栏是为**案件群**写的——那里案子是活的、有承办律师在跟，
   替他对本案下结论是越界。而一个刚扫码进来的陌生人，说的每一句都是
   「我这个事」；在进线窗口恪守它，等于对着来咨询的人一个问题都不答，
   首轮筛查根本无法成立（律所方原话：「尽可能帮客服做 screening，了解案件详情」）。
   例外只放开「答不答」，不放开「答什么」：紧急/费用/案件进展仍一律承接，
   模型仍只给一般性框架并保留 `[[NEED_LAWYER]]` 示弱出口，出口闸门不变。

## 三分类判断规范

`responder/engine/rules.py`，分层命中即停，优先级：
非文本/空 → 沉默；@点名 → 沉默；紧急 → 承接(urgent)；费用 → 承接；案件特定 → 承接；
找人/催回复 → 承接；自指本案 → 承接；通用法律问题 → 直接回答；其余 → 沉默。
拿不准时倾向沉默——AI 是补位，不是抢答。沉默也必须写入判断日志。

responder-api                    # 启动服务（默认影子模式）

## 验证协议

**功能「完成」的唯一标准是 `python scripts/verify.py` 对真实产物通过**：

- 测试集 ≥ 200 条脱敏消息（`tests/data/test_messages.jsonl`）
- 三分类准确率 ≥ 95%
- 生成回复对禁止事项清单零命中
- 直接回答类免责句式覆盖率 100%

**禁止无脚本输出的完成声明。** 修改判断规则或话术后必须重跑 verify + pytest。

## 自主循环边界

- 可无人值守：基础设施、测试、重构、日志/存储/控制台功能。
- **必须人工审核后合并**：话术模板（`reply/templates.py`）、prompt（`reply/prompts.py`）、
  语感规范（`docs/voice-guide.md`，模板与 prompt 的话术依据，三者须同步演进）、
  判断阈值（等待时长/接管时长/升级时长/复核置信度）、
  线索优先级权重与门槛（`engine/priority.py` 与 `docs/lead-routing.md` 须同步演进）、
  合规文本（`compliance/forbidden.py`、`compliance/disclaimer.py`）、测试集标注变更。

## LLM 层架构约定

- 双供应商：DeepSeek（默认，成本考虑）与 Anthropic 可切换（`engine/llm.py` 的 resolve()）；
  两条后端共用同一套 prompt 与净化/合规闸门，新增供应商必须走同一出口。

- system prompt 保持完全静态（不插时间/ID），一切易变上下文进 user 消息（`reply/prompts.py`）。
- 模型只能在「漏答方向」纠偏：仅复核规则判 default-silence 的边界样本；
  紧急/费用/案件特定/自指等高优先级规则命中不得交模型改判。
- 模型有示弱出口 `[[NEED_LAWYER]]`：答不稳一律转承接，禁止移除该机制。
- 所有模型输出必须过 `reply/sanitize.py`（形态）+ `compliance/guard.py`（语义）双重闸门。
- 任何 API 异常/拒答/解析失败必须静默降级到确定性路径，不允许让客户等待或看到报错。
- 配置好 API key 后跑 `python scripts/prompt_smoke.py` 人工审阅真实话术质量。

## 已定业务决策（2026-07，不要反向修改）

- 客户群已在企微，接入方案见 `docs/integration.md`（微信客服 / 机器人 / 会话存档 / 影子模式）。
  **已实测**：自建应用回调收不到群聊内容；微信客服是唯一免费且全自动的进线通道，为首选。
  客服会话复用群档案模型（`kf:{open_kfid}:{external_userid}`），首次进线自动建档。
- 试点：劳动仲裁/法律纠纷群；AI 处理追问时同话术不复读（`service.Pipeline._apply_followup_policy`，依据 `Store.count_recent_live` 的三级策略），转升级提醒。
- 分案体系（2026-07）：筛查后的线索按 `docs/lead-routing.md` 评分（P0/P1/P2）并自动派给
  具体律师（按在办量，不看专长）；律师个人令牌只看自己名下数据（`console/api.py` 服务端强制）。
  律师名册为空时整套派单回落旧链路——该回落行为是升级兼容承诺，不得移除。
- AI 身份：普通销售顾问，不明示 AI（全量留痕是该决策的合规兜底，留痕逻辑不得削弱）。
- 免责句式默认关闭（见上）。
- 一对一进线的两个收口动作（2026-07，依据抖音后台漏斗 进私 416 → 开口 90 → 留资 50）：
  ① **进线即问候**：客户扫码/私信进来触发 enter_session 事件就先打招呼，不等他开口
  （`worker._kf_welcome`，按 msg_id 幂等，回访客户不再自我介绍）。
  一通对话只许有一次开场白，第二次一律改走承接（`service._avoid_repeat_greeting`）。
  **`kf_welcome_on_enter` 2026-08-12 起默认关闭**：企微后台「微信客服 → 欢迎语」
  已经配了一条，客户进会话时企微自己会发。我们再发一条，客户连着看到两句招呼——
  那恰恰是「一看就知道是机器人」最典型的样子。**一个窗口只该有一个人在说话。**
  机制保留：后台没配欢迎语的部署方式打开开关即可用。
  代价是那条开场白里的两样东西（例句、「咨询是免费的」）没人说了，
  所以它们要挪进企微后台那条欢迎语的文案里——那是律所自己填的，不归代码管。
  ② **聊够了主动要电话 + 邀约到所**：默认第 3 条客户发言后，且通篇未出现联系方式、
  未成交客户、接管窗口内没问过（`service._should_ask_contact` → `templates.ask_contact`）。
  阈值 `ask_contact_after_messages` 与所址 `office_address` 走配置，改动须人工确认。
  ③ **每条回复都要有下一步**（业务决策 2026-08，律所方明确要求）：承接话术
  「我帮您问下律师，请您稍等」是死胡同，客户看完只能干等，很多人就这么走了。
  三档推进依次升级、互不复读：轻推（`templates.next_step`，承接回复后缀）→
  完整邀约（`ask_contact`，含所址与面谈邀请）→ 静默挽留
  （`worker._sweep_winback`，一通对话只发一次）。轻推不阻断完整邀约——
  后者多出的是所址，属新信息不算催单，故两者用不同标记判重
  （`ASK_CONTACT_MARKERS` / `OFFICE_INVITE_MARKERS`）。
  三档**只在一对一进线窗口生效**：群聊里承办律师本人在场，AI 追着要电话越界。
  **条间隔 3 秒**（`split_delay_seconds`，2026-08-12 律所方定；原 1.5 秒）：
  「一股脑发出来」是客户认出机器人最直接的一条线索，比措辞本身更明显——
  真人打一句话要想一下、要打字。**首条不等**：首响时长是北极星指标，
  让客户干等换不来任何东西，要放慢的是「后面几条之间」。
  **④ 邀约到所排在要电话之前（2026-08-12，律所方复盘后拍板）**：
  律所方跟所里同事对过账——**真正高客单价的单子几乎都是线下见过面之后才签的**，
  线上聊得再好也只是筛查。所以收口第一拍是「请他来所里」，
  号码是他没接这一茬时退而求其次的第二拍。从大到小是让步，读起来自然；
  反过来先要号码再请人跑一趟是层层加码，客户会觉得被追。
  `office_invite` 三样东西缺一不可：**谁接待**（`office_senior_title`，
  默认「主任律师」——稀缺性是客户愿意专程跑一趟的主要理由，一句
  「律师会接待您」换不动任何人；留空即不提，因为律协禁止虚假宣传，
  这句必须是真的）、**带什么**（带材料，一个具体的准备动作比空邀约有效得多）、
  **没有压力**（「聊完您心里有个数，接下来怎么走再定」）。
  **⑤「免费咨询」由律所授权说出口（2026-08-12，律所方拍板）**：
  律所方要求主打免费法律咨询。我两次提出全国律协《律师业务推广行为规则》
  第十条把「以不收费或减低收费招揽业务」列为禁止行为（法律援助案件除外），
  律所方重申「你不要管，按我说的做」。**这是律所的执业判断，由律所承担，
  已照办并记录在案。**

  落法上有一条不让步：**只放行律所逐字定下的那几句，不拆费用闸门。**
  `Settings.approved_claims`（`|` 分隔，**列表第一句是主打的那句**）里的原话
  在 `forbidden.check()` 里先被抠掉再跑规则，
  于是**授权的那句能说，别的关于钱的说法一句也漏不过去**——
  「打三折」「代理费一万」「按标的额百分之十收」照拦。
  拆掉闸门的后果是模型自己编出律所没授权、也不知情的价格承诺，
  那比不说更糟。改 `approved_claims` 等于改一次对外承诺，须律所方本人确认。

  **2026-08-12 律所方定稿：主打「免费咨询」**（`免费咨询|咨询是免费的|首次咨询免费`，
  第一句即默认）。另注意「资讯」与「咨询」拼音完全相同，输入法会挑错——
  而「免费资讯」是免费的新闻消息，不是免费的法律咨询。
  `test_the_homophone_never_reaches_a_customer` 守着这一条。

  说的位置有三处，都挑在客户会犹豫的那一刻：**开场白**
  （漏斗最贵的断点——416 人进私信只有 90 人开口，挡住他们的除了
  「不知道怎么说」就是「随便问一句会不会要钱」）、**邀约到所**、**静默挽留**。
- 对客称呼（2026-08，律所方要求）：**一对一进线的对话里不点名具体律师**
  （`templates._lawyer` 对 `is_kf` 一律返回「律师」）。不是措辞偏好——
  谁接这单由分案引擎按在办量算出（`docs/lead-routing.md`），而客服/私信
  建档时的 `lawyer_name` 只是 `kf_default_lawyer_name` 这个配置默认值，
  两者常常不是同一个人；说「魏律师会给您回电话」而实际派给别人，
  客户等的是个不会来的电话。群聊相反：那里的名字人工维护且律师本人在场，
  点名是对的，不得一刀切抹掉。
- 渠道措辞：「在群里」只对群聊说。客服/私信是一对一窗口，没有群，
  模板一律经 `templates._in_group(group)`，prompt 经 `is_one_on_one` 告知模型当前场合。
- 抖音企业号私信（2026-08，见 `docs/douyin.md`）：用户 first pass 多在抖音而非微信
  （微信要先扫码，多一个动作）。判断层与微信客服同构（`is_kf` 对抖音会话亦为真），
  差异全部收在发送层。**平台硬限制写死在代码里，不得放宽**：只能回复不能主动发起、
  客户发言后 24 小时窗口、窗口内最多 6 条（按分条后的真实条数算，
  `replies.parts` + `Store.sent_parts_since`）、进会话事件 30 秒内响应。
  超发的代价不是少发一条，是应用被平台标记，故 `service._douyin_budget` 宁可少说一句。
  发送 endpoint 因文档站不可达而做成配置项，由 `scripts/douyin_smoke.py --probe` 校正。

- 会话转接（2026-08，见 `docs/kf-handoff.md`）：客户一做出「想找真人」的动作就把微信客服会话
  转给分案引擎派出的律师（`service._maybe_handoff` → `kf.service_state/trans`），
  取代「律师打电话」这一最脆的环节。**六个前提缺一不可**：开关开、微信客服会话
  （抖音无对等能力）、本会话未转过、**客户做出了「想找真人」的动作**、
  已派给具体律师、且该律师确实是该客服账号的接待人。接待人校验必须在过渡话术
  **之前**——话发出去客户就真的在等了。转接失败一律静默回落原链路且**不落库**
  （落了库 AI 就闭嘴，而那头根本没人）。转接后 `gate:handed-off` 让 AI 沉默，
  超过 `handoff_reclaim_seconds` 无人接手则回收给 AI。过渡话术不点名（同上条），
  并给一个此刻能做的下一步（先发材料）。就绪自检在控制台「状态」页一键可查。
- **律所侧要维护的名单只有两份**（2026-08-12，律所方原话：「我们应该只有两个名单，
  为什么现在有三个名单？」）：① 律师名册（控制台「团队」页，律师就是客服）；
  ② 企微后台「微信客服 → 升级服务」的成员范围（推名片用，我们只能读不能写）。
  企微客服账号的**接待人**是第三份，但它的正确内容永远等于 ①，因此由
  `responder/kfroster.py` 自动同步：名册一改打脏标记（`Store.upsert_lawyer` /
  `delete_lawyer`），后台 `_sweep_servicers` 同步，外加 `kf_servicer_sync_seconds`
  兜底修复有人在企微后台手工删接待人造成的漂移。**不要把它变回一件要人记着做的事**——
  靠人记得点按钮，等于把一次静默失败（转接被企微当场拒）押在记性上。
  保存律师时刻意**不**同步调企微：接口一超时就会让「加一位律师」跟着失败，
  而名册其实已经存好了。
  **「静默回落」不等于「不留痕」**（2026-08-09，律所方原话：「那怎么会没有自动转接给律师呢」）：
  六个前提原本是六个静默的 return，转不成控制台里什么也看不出来，只能一条条猜。
  现在每一道都经 `_skip(reason)` 落一句人话——写日志、写 `handoff_skip:{group_id}` 小记、
  进当轮判断日志、并在「为什么没回复」里直接显示。**不许再新增静默的 return。**
  **转不转看清单，不看分数**（2026-08-09 律所方拍板，`priority.WANTS_HUMAN`）：
  说要委托 / 想来面谈 / 要律师联系他 / 有人受伤住院 / 要加微信 / 留了电话 —— 任一即转；
  只问法律问题、只问收费、只打招呼不转。分数（P0/P1/P2）退回它本来的职责：
  **排队顺序与看板统计**，不再当开关。理由：分数回答「先给谁打电话」，
  转接回答「现在要不要叫真人」，绑在一起就会出现真机那一幕——
  客户说了「让律师给我打电话」，系统还在算他够不够 60 分。
  原来那道门槛是怕转太多，而 `handoff_grace_seconds`（90 秒无人接手 AI 自动接回）
  落地后这个顾虑已不成立：**代价变了，规则就该跟着变**。

  **企业名下不是每个客服账号都归我们管**（2026-08-09 真机）：律所另有一个
  「上海松沪律师事务所在线客服」人工在接，从没交给自建应用托管，而
  `kf/account/list` 照样把它列出来。对它做任何管理动作都是 `48007
  no kfid privilege`。判据用 `_kf_accounts_in_use`＝**有客户从这个账号进来过**
  （库里有会话），没有会话的账号一律跳过、不判红、不去动它。
  一条会话都没有时（刚上线那天）退回「全都查」。
  原因：**说错「坏了」和漏报一样贵**——人会跑去修一个没坏的东西，
  而那天恰好是 demo 日。企微错误码一律经 `wecom_kf.err_hint()` 翻成
  一句带后台路径的中文，别让律所方对着 48007 发愣。

  同批修掉一处真 bug：冷消息的重算分支算完分就 return，从不检查转接。
  而硬信号（有人受伤、要联系方式、留电话）恰恰最常落在冷消息里——
  症状是控制台里线索明明 P0，律师企微里什么都没有。
- **转接之后再推一张名片（2026-08-12，律所方要求）**：转接成功后调
  企微「升级服务 → 专员服务」（`kf/customer/upgrade_service`，type=1），
  把**分案引擎算出来的那位律师**的名片推进对话。
  律所方原话：「即使对接了人工，但依旧用的不是客服自己的企业客服号沟通的」——
  问得准。**转接只解决「谁来回这句话」，名片解决「客户认识了谁」。**
  微信客服里律师回的话，客户看到的永远是客服账号在说话；会话一结束联系就断了，
  律师之后想主动找他没有任何通道。客户把名片加上之后就是长期联系人关系——
  对律所来说这是从「一次咨询」变成「长期关系」的那一步。
  三条约束：**推分案算出来的那一位**（企微后台那个「随机推荐专员」会把
  劳动争议的客户推给做刑事的律师，比不推更糟）；**推荐语留空**＝用企微后台
  配好的那句，话术不写进代码；**失败一律吞掉**——这一步锦上添花，
  不能反过来把已经成功的转接搞砸，但要落 `specialist_card:{gid}` 小记
  并在「为什么没回复」里报出来（最常见的失败是 `95021`＝这位律师不在后台
  「升级服务」的专员名单里，而它的表现是「客户什么也没收到」）。
- **稳定性三件套（2026-08-10，律所方：「先把稳定性跑好」）**：
  ① **后台线程心跳**（`Worker._beat`，每轮一次，落 `worker_heartbeat` 小记）。
  线程停了是全系统最致命也最安静的一种坏：队列照常收，只是再也没人取——
  所有客户从此一句回复都收不到，而别的每一个指标看着都正常。
  `/health` 报 `worker_alive` / `worker_idle_seconds`，「为什么没回复」直接判定，
  并把「活着但半天没跑一轮」（多半卡在外部接口）和「死了」分开——修法不同。
  ② **看门狗**（`Worker._watch`，5 秒一探）：线程没了就地拉起来，不等人发现。
  重启是安全的——队列属于 Worker 不属于线程，游标/待办/提醒都在库里，
  最坏是一条消息重复处理一次而入库按 msg_id 幂等。**重复一句远比永远静默便宜。**
  ③ **升级能把自己撤回来**（`ops._SCRIPT`）。这是唯一能让服务器永久失联的路径：
  律所侧没有 SSH，控制台和后台线程在同一进程里，新版本一旦起不来 →
  服务死 → 控制台打不开（那个「升级」按钮也没了）→ 后台线程不跑 →
  自动升级不跑 → **再也推不进任何修复**。而「推送即上线」意味着这条路每天走好几趟。
  三道闸：装完先在另一个进程里 `create_app()` 装配一遍（配置校验、数据库迁移、
  所有 import 都在这步暴露）→ 起不来就不重启，直接回滚；重启后轮询 `/health`，
  60 秒不通同样回滚并重启回旧版；全过程写进升级日志。
  **宁可停在旧版本，也不能停在一个起不来的新版本上。**
  `test_the_app_actually_assembles` 与升级脚本用的是同一句冒烟检查，必须常绿。
- 自动升级（2026-08）：服务器每 5 分钟自查远端分支有无新提交，有则自行拉取重启
  （`ops.auto_update_tick`，worker.tick 调度）。原因是运维侧未必够得着这台服务器，
  但服务器够得着 GitHub。**推送即上线**，因此 push 前必须 pytest + verify 全绿——
  没有人工点按钮这一道闸了。重启会丢内存队列，故队列非空或客户 2 分钟内说过话时跳过。

## 外部渠道接入（2026-08，见 `docs/channels.md`）

律所的获客渠道远多于「有官方 API 的渠道」：美团、点评既无开放接口，
也不允许把人引到站外。RPA（影刀/龙虾这类）能替人点那些按钮。
`gateway/channel.py` 是给这类工具的通用进出口。

**核心取舍：RPA 只是一只手，不是一个脑子。** 对接方只做搬运
（`inbound` 交消息 / `outbox` 取话 / `ack` 销账 / `heartbeat` 报到），
判断、生成、合规、评分、派单全在我们这一侧。**自动化工具里不许出现任何话术。**
否则每个渠道会长出一套自己的规则，三个月后同一个「顾问」在五个平台上
说话不像同一个人；更要命的是禁止事项清单只挡得住经过我们出口的文字。
换 RPA 产品的成本因此接近零——改的只是那三个 HTTP 调用的调用方。

- 外部渠道会话 `ch:{channel}:{external_id}`，`GroupProfile.is_external`，
  且 **`is_kf` 为真**——判断层与微信客服同构是整套多渠道方案的地基：
  **多接一个渠道，不该多一个合规缺口，也不该多一套话术。**
- **回复落发件箱（`outbox` 表），不靠 HTTP 同步返回。** 那头一次超时，
  那句话就永远消失了，而客户还在等。`inbound` 顺手带回待发条目只是快捷路径。
  销账等对方明确 `ack`：**宁可重发一句，不可丢一句。**
- 鉴权用独立的 `channel_token`，**不复用也不回落到 `admin_token`**：
  RPA 跑在一台随时可能被人碰的桌面电脑上，令牌等于摊在那儿。
  令牌未配 = 接入口关闭（默认拒绝，不是默认放行）。
- 建档时必须落 `lawyer_userid`（外部渠道没有「接待人」可查，用全局兜底）。
  留空的后果是线索照样入库评分，但那张交接单一个人也收不到——
  即 2026-08-06 那条最贵的静默失败。
- 渠道标识只许小写 slug（要进 group_id 主键），中文名走 `label`。
- `ext_channel` 同时是**线索来源**（`exporter._source`）：没有它，
  所有从微信客服进来的人在后台长得一模一样，投三个月也说不清哪个渠道该加钱。
- **`worker._sweep_channel_health` 不是可选项。** RPA 停摆是静默失败：
  客户在等，后台一片安静、日志里连一行错误都没有。两类告警分开报——
  回复积压发不出去（分钟级）、渠道完全没心跳（小时级，半天没客户是正常的，
  半天连不上不是）。报过一次记 `alerted_at` 防轰炸，那头恢复自动清零。

## 词表回测与「敏感即转人工」（2026-08-10，律所方要求）

律所方原话：「让 AI 偏向自由回复，不要给它设那么多限制，但同时我们又能
检测到一些关键、敏感的词汇……比如你们地址在哪 / 你们怎么联系 /
你们收费是多少，这类直接转人工」。

**`scripts/backtest_kf.py` + `tests/data/kf_backtest.jsonl` 是这条要求的量具**
（116 条手写语料，每条带业务理由）。它跟 `verify.py` 分工不同：verify 按
群聊口径守三分类准确率；这份守**进线窗口**，而那里的正确答案跟群聊相反——
群里承办律师在场，AI 拿不准就闭嘴是对的；进线窗口没有别人，闭嘴就是丢单。

两个维度分开算，因为**「答一句」和「叫个人」是两件事，而且经常该同时发生**：
客户问「你们地址在哪」，正确做法是当场把地址给他（答案就在配置里，
让他等一个律师回电话是荒唐的），**同时**把会话转过去——问路的人下一步就是上门。
把这两件事混成一个标签是这份回测第一版就犯的错，改对之后基线从 77% 跳到 100%。

首轮结果：客户看到什么 77% → 100%；该不该叫人 71% → 100%。落地的四件事：

1. **敏感即叫人**：`office`（问所址/路线/几点上班）作为新信号加入
   `priority.WANTS_HUMAN`，`fee` 也加进去。fee 这条我原先反对
   （「问收费说明案子值钱，不说明客户想找人」），律所方判断相反且他们是对的：
   问价的人已经在比较，而比较时听到的是不是真人直接决定他去谁那儿。
2. **成交类问题一律承接**（`ENGAGE_PATTERNS` / `MEETING_PATTERNS`，
   仅 `is_one_on_one`）：怎么委托、你们能不能接、谁来办、做过类似案子吗、约见。
   理由不是它们敏感，是 **AI 答了没有说服力**——客户这一刻挑的是「要不要
   把事交给你们」，他要听一个具体的人；AI 说「我们经验丰富」只会让他更想
   问一句「你是机器人吧」。留手机号（`contact-left`）同档。
3. **自由回复**：进线窗口里命中法律话题**即作答，不再要求是问句**
   （「公司拖欠我三个月工资」没有问号，可他显然要一个答复）。群聊维持原样。
   配套：`_maybe_intake` 改用「他在陈述还是在提问」分流——陈述就接着问
   （这时我们几乎什么都不知道，一个好问题的信息量远大于一段好答案），
   提问就正面答。
4. **词表只写一遍**：`signals` 直接复用 `rules` 的 ENGAGE/MEETING/FEE/
   WANT_CONTACT 模式。各写一套的代价回测里量出来了——规则层认得
   「留个电话给我」，信号层不认得，于是 AI 承接得好好的、**转接一次也不触发**。
   一致性由 `test_the_two_wordlists_cannot_drift_apart` 守着。

顺带修掉三个正则误伤，全是「裸字符太松」：
`FEE_BROAD` 的裸「费/价/点」把**我们自己的商品名**（「…30分钟免费法律咨询」）
判成客户问价（导入历史客资每条白加 15 分），把「你们几点下班」判成问收费；
裸「免费」同理。**改动词表时先跑这两个脚本**，再跑 pytest。

## 整链复查：九条「静默丢单」路径（2026-08-10）

律所方原话：「我们不能为了提效，反而导致原本会成交的客户没有成交。」
按这个标准把「进线 → 回复 → 评分 → 派单 → 转接 → 接手」整条走了一遍，
九处全是**同一种失败**：系统自认为做完了，客户那头什么都没发生，
而后台一切正常。**它比崩溃贵得多——崩溃有人看得见。**
回归测试在 `tests/unit/test_lossy_paths_0810.py`。

1. **客户的话被记成「我方发言」**（最严重，很可能就是真机「连发五次你好全程静默」
   的元凶）。判据曾是 `origin == 5 or bool(servicer_userid)`，而企微在
   **客户消息**上也会带 `servicer_userid`（标明会话归谁接）。于是客户自己说的话
   走进 `handle()` 的 staff 分支：就地标记已转人工 → AI 从此闭嘴 →
   一个字的回复也没有，判断日志里却每条都写着「staff-message，不需要 AI 回」。
   **origin 是企微专门用来回答这个问题的字段，缺失时才回落启发式。**
2. **`has_greeting` 把没发出去的回复也算成「已经开过口」**（判据是 replies 表
   有没有行，不看 mode）。一条 `failed` 或 `shadow` 就让 AI 认定打过招呼了，
   从此不再自我介绍、也不再补问候——空窗口是最大的流失点，而这个判据
   曾经亲手制造它。改为只认 `mode='live'`。
3. **过渡话术没发出去仍然转接**。转了 `gate:handed-off` 让 AI 闭嘴，
   律师还没露面，客户从头到尾一个字没收到。**比不转更糟**——不转的话
   AI 至少还在陪着。现在发不出去就不转。
4. **进线问候没发出去却记了账**，后果同第 2 条。现在失败落 `failed` 行 + 运维小记。
5. **第三次追问在一对一窗口彻底静默**。静默是为群聊写的（律师在场，再说是刷屏），
   而进线窗口里没有别人：客户问了三遍还是同一句，说明他越来越急，
   **这时候闭嘴是最坏的回应**。改为 `templates.third_touch`：换个说法 + 给一件
   此刻他自己能做的事。群聊不动。
6. **单条消息处理异常后游标照常推进**，那条消息永远不会再来。
   加 `_rescue_failed_kf_message`：发一句确定性兜底 + 落运维小记。
   救援自身再炸也只吞掉——它已经是最后一道。
7. **交接单推不出去不响**。不标记已通知（所以会重试）是对的，但一直失败时
   那张单一辈子送不到，而后台显示「待跟进」一切正常。加 `logger.error` + 小记。
8. **Excel 导出可被注入公式**。客户诉求是客户自己打的字，`=1+1` 在表里会变成 2；
   而这张表会被转发给合伙人、发进微信群。前缀单引号中和。
9. **导出表的深链还是 `/ui#g=`**（企微把 `#` 转义成 `%23` → 404），
   而这张表就是拿去转发的。统一成 `/g/{id}`。

顺带：**抖音回调改为默认拒绝**——原来「没配 Token 就不校验」，
等于把一个公网地址敞开，任何人都能灌进伪造的客户消息、生成假线索、
占满律师队列。与外部渠道接入口口径一致。

## 全链路体检落地（2026-08-12，律所方：「全部修复」）

六个视角并行审计 + 逐条独立证伪（剔除 3 条假警报）之后落地的一轮。
**结论性的一句：不乱说话那部分做得比多数同类扎实，缺的是另外两件——
客户已经点头的那几秒，和出事之后没人会知道。**

### 客户点头之后的那两秒（最贵的三条）

1. **一声「好的」不能等于沉默**（`rules.classify(awaiting=)` + `templates.affirm_followthrough`）。
   AI 发完完整邀约，客户回「好的」，旧版由 `_CHITCHAT` 快速通道判成闲聊、
   **一个字都不回**。没约哪天、没说带什么材料；半小时后补发的挽留，
   内容恰好是把他刚答应过的事再邀请一遍。判据只看**最后一条实发回复**
   （隔了几轮的「好的」谁也说不准答的是啥），且仅一对一窗口。
   词表比闲聊窄：**只收「他答应了」，不收「谢谢/辛苦了」这类收尾语**。
   这次点头还要作为 `meeting` 硬信号进线索（`signals.scan(extra_hits=)`），
   并绕开冷消息早退——首次进线那一刻库里没有线索行，走冷分支就地丢掉的
   恰恰是漏斗上最值钱的那个动作。
2. **客户把号码打出来，第一句必须是「收到了」**（`templates.contact_received`）。
   旧版走通用 CONTACT 承接，三条变体里两条开口是「律师这会儿应该在忙」。
   同时裸手机号不再判成「在催」——判成催会回「抱歉让您久等了」，
   而他没在等，他刚给完号码。
3. **「免费咨询」的口径**：`templates.free_claim()` 是那句原话的**唯一真相来源**，
   七处硬编码全部改从 `approved_claims` 取。闸门靠「与授权原话逐字相同」放行，
   谁润色一下，整条邀约会被当成报价整段丢掉——地址、主任律师、带材料、免费
   四样一起没。客户反问「你们咨询要钱吗」由 `consult_is_free` 正面答
   （仍算 `fee` 信号照常转人工）；必须带疑问标记，否则我们自己的商品名
   「30分钟免费法律咨询」会重新被判成客户问价。费用承接里那句「来所里坐坐」
   已拿掉：它命中 `OFFICE_INVITE_MARKERS`，会压掉唯一那条正式邀约。

### 数据边界（最严重的一条）

**「该通知谁」和「这是谁的数据」必须是两个字段。** 微信客服建档时把企微返回的
第一位接待人填进 `lawyer_userid`，而律师工作台正是按它放行的——名册里排第一的
那位普通律师，个人链接一点开就能看到全所每一通咨询原文，还能把任意客户的会话
「转给我」。现在 `lawyer_userid` 只表示数据归属（分案引擎派单或人工指定时才写），
建档一律只落 `notify_userid`；取值顺序统一走 `GroupProfile.reminder_userid`。

配套：弱口令去掉「够长就放行」的口子（文档里那句示例 `songhu-jiufeng-88` 恰好
17 位，绕过了 `<16` 的判据），**示例口令本身也在拒绝表里**并由测试守住一致性；
撞令牌到全站闸一半时推企微告警；`enable-https.sh` 补 `TRUSTED_PROXY_HOPS=1`
与 nginx 转发头（少了它，nginx 一挡在前面，登录锁定从按人分桶塌成全世界一个桶）。

### 三处「无限重试」（`responder/retry.py`）

共同点是**失败没有代价上限，而重试本身反过来把系统弄坏了**：
加急提醒每 10 秒重试上百次，占满处理所有客户消息的那唯一一条线程并把企微打到
限流——之后交接单、督办、战报、告警全部一起静默失效，**系统亲手拆掉了告警链**；
挽留每 10 秒重发连打 24 小时并把抖音配额算光；自动升级把起不来的版本每 5 分钟
重放一次、永远出不来。统一改成有限次 + 退避 + **放弃时落一条控制台看得见的小记**。
失败过的 commit 拉黑（推新提交即恢复），升级日志改追加。

### 出事有人知道

每日战报固定一段「系统自检」（线程停摆 / 看门狗重启 / 升级被拉黑 / 所有试到放弃的事）。
**零线索那天尤其要出**——「昨天没有新线索」正是通道断掉时的症状，
而那条分支原来直接 return，把唯一那份健康报告漏在了最该看到它的那天。
`sync_msg` 失败当场重试两次并计数；线索链路抛异常时落痕 + 让逐条提醒顶上
（否则交接单和提醒会**同时**消失，这个客户在律师那边彻底没有痕迹）；
判断日志挪到线索链路之后落库，否则「为什么没转」那几条理由一条都记不进去。

### 个人信息

- `llm_provider` 默认从 `auto` 改成 `deepseek`，且 **`auto` 不再自己滑到境外那家**。
  DeepSeek 的 key 掉了、环境里恰好还有个 ANTHROPIC_API_KEY，旧写法会静默地把
  客户的咨询原文改发出境——那不是换个模型，是从「向第三方提供」变成
  「个人信息出境」。换处理者必须是一次明确的配置。
- `retention_days`（默认 0＝不清理，**刻意的**：保留多久是律所的业务决策）
  + `Store.purge_older_than`，已成交客户一律不动，清理留痕。
- `templates.privacy_notice()` 是给律所粘进**企微后台欢迎语**的告知草稿，
  代码不发这一句（一个窗口只该有一个人在说话，且这是律所署名的法律承诺）。
  控制台「状态」页可一键复制。
- `forget_group` 按后缀全清运维小记与重试计数，不再逐个列举——
  它现在也是收到删除请求时唯一的执行入口，「差不多删干净」是一句不实的承诺。

### 判定与话术的四处误伤

「我要去劳动局投诉他们」不再当成投诉律所（裸的 `要.{0,4}投诉` 已收窄）；
紧急路径改用 `urgent_next_step`（通用那句「律师一有空就给您回电话」当场否掉了
「已加急」）；模型降级话术补变体并**复述客户问的是什么**，降级比例进计数器；
企微「发送失败」事件回写 `mode='failed'`，让追问/挽留重新生效——
不处理的话库里标着「已发送」、控制台显示「AI 已回复」，而客户一个字没收到。

## Demo 前的整链路复查发现（2026-08-06）

按「一个客户从进线到律师接手」实测一遍，四处必须记住的：

1. **交接单曾经一条都发不出去**（最严重）。名册为空 + 兜底接收人为空时，
   线索照样入库、评分照样算，但那张交接单**一个人也收不到**——控制台里
   一切正常，律师那边什么都没有。**静默失败是最贵的 bug**，因为没人会去查
   一个「看起来正常」的系统。已加 `opscmd._op_add_lawyer`：加人同时把兜底
   接收人补上（原本为空时）。
2. **客户第一句就说事时，AI 让他再说一遍**。`default-silence` 在一对一窗口
   的兜底是引导型开场白（「麻烦您把情况讲一下，比如『准备离婚…』」），
   而客户刚说完「公司拖欠我三个月工资，还把我辞退了」。现按
   `rules.has_substance` 分流：有内容 → 承接/追问（`kf:substance`），
   只打招呼 → 开场白。判据故意放宽——说了却被要求重说是最伤的，
   反过来误判只是多问一句，不难看。
3. **自报家门不能挂在开场白话术里**。改走承接路径后那句律所全称就丢了，
   所以拆成 `templates.intro_line`，由 `service._with_intro` 在本会话第一条
   回复上加一次（紧急消息除外：人正急着，先安抚）。判据是
   `Store.has_greeting`＝**本会话有没有回过话**，不是「有没有发过 greeting
   类回复」——后者永远为假，会导致每条回复都报一遍全称。
4. **「我想找律师」原本不算委托意向**，线索因此停在 P1、转接不触发。
   已加入 `signals._ENGAGE`。


## 真机复盘（2026-08-07，交通事故咨询实测）

律所方跑通一整通对话，暴露四处。**共同根因：规则用了封闭枚举**——
客户的说法是无穷的，穷举必然漏，而漏掉的那条永远是**静默地**漏：
回复看起来正常，没人会去查。

1. **「赔偿大概多少钱」被判成费用咨询**，AI 回了一段「我不能报价」。
   客户问的是**他能拿多少**，我们答的是**我们收多少**。这是人身损害与
   劳动争议里最常被问的一句。已加 `rules.CLIENT_MONEY`：费用层只管
   「我们收多少」，客户自己的钱是法律问题（`client-money-question`），
   同时把它并入通用法律话题的判据——问的是权利，不是收费。
   反向护栏保留：同句出现律师费/代理费/咨询费仍走费用承接，AI 绝不报价。
2. **「交通事故责任怎么认定」落进默认沉默。** `QUESTION_HINT` 里
   「怎么X」是 `怎么(办|判|算|赔|分|处理|规定)` 的枚举，「怎么认定」
   一个字不在表里，整条掉出去。改成开放式 `怎[么样]|什么|哪些|…`。
   **多召回的代价只是多答一句**（后面还有合规闸门与模型示弱出口），
   漏掉的代价是客户被晾在那儿。
3. **「地址在什么地方」回了「会转给律师」**，而地址就在配置里。
   加 `rules.OFFICE_FACT` + `templates.office_fact`：**能当场答的绝不推给人**，
   每一次推诿都是一次流失。不进模型（让模型复述确定的地址只是多一个说错的机会），
   未配地址时明说「确认后回您」——说错地址比不说更糟，客户会白跑。
   **只在一对一窗口生效**（`classify(is_one_on_one=)`）：案件群里
   「地址发我一下」多半问的是法院的地址，甩律所地址过去是自信地答错。
4. **客服只收到过那一条弱意愿提醒。** 客户是边聊边变强的（留电话 40 →
   问赔多少 +15 → 说要委托 +35），而旧策略只认冷/温/热三档意向，
   这些变化全在「温」里。已加 `lead.tier_upgraded`：**弱 → 强再响一次**，
   前缀「【升级】」以免被当成重复推送划走。反向不通知（分数会波动，
   「刚才急现在不急了」推给人只消耗信任）。配套：`service._maybe_dispatch_lead`
   对冷消息也重算分数（原来直接 return，于是后续加分一次都没记进去）。

另有两处并非规则问题：

- **交接单里的「看完整对话」在企微里点开 404。** 原链接 `/ui#g=<id>`，
  **企微把 `#` 转义成 `%23`**，服务器看到的路径成了 `/ui%23g=...`。
  浏览器里永远测不出来（浏览器不转义 `#`），只有真机点一次才现形。
  改走普通路径 `/g/{group_id}`。注入面：`json.dumps` 不转义 `</script>`，
  必须额外转义 `<`——这条链接谁都能构造了发给律师。
- 阈值本身未动。「留电话 40 分 < P0 门槛 60」是**业务判断**，
  待律所方拍板（见待定决策）。

## 首轮筛查要持续作答（2026-08-07，律所方要求）

律所方原话：「是否能够一直为客户解答基本的法律问题？因为我们要尽可能帮客服做
screening，了解案件详情」。

实测发现的堵点不在话术，在分类：**通用法律话题靠关键词白名单命中，
而追问几乎从不重复话题词**。客户开头说了「交通事故」，接着问
「那我该准备什么材料」「如果对方不赔怎么办」「调解不成还能怎么走」——
一个法律词都没有，于是全部落进默认沉默。而这些恰恰是筛查最需要的对话：
**客户每答一句，案情就清楚一分，交给客服的那张单就厚一分。**

`Pipeline._in_consultation` → `rules.classify(in_consultation=)`：进入咨询状态后，
判据从「命中话题词」放宽为「这是不是一个问句」。三个前提缺一不可——
一对一窗口、未成交、且客户确实把事说出来过（只打了个招呼就放宽，
等于对着一句「在吗」大谈法律，那不是热情，是没听懂）。

放宽的是「答不答」，不是「什么都能答」：紧急、费用、案件进展三层一个没动，
闲聊仍沉默，模型仍只给一般性框架。

**回一句话就接管**（同批）：一对一窗口里客服/律师说的第一句话直接记成正式转接
（`service.handle` → `set_handoff`），不用开控制台、不用点按钮——他本来就要打字，
那句话本身就是接管动作。交接单末尾写明这一点：功能做了却没人知道等于没做。
群聊不适用（律师在群里发言是常态，标成已转接会让 AI 从此在群里失声）。
配套：接手的人正在说话时不再触发「超时回收」——那会变成客服聊到一半 AI 插进来抢话。

## 老客户回访不能静默（2026-08-07 真机第二轮）

律所方用一个**之前聊过的账号**再来一通：AI 答得没问题，但**后台一条报告都没有，
摘要也没更新**。三个 bug 叠在一起：

1. **回访推送的判据错了。** `should_notify` 认的是「意向档位升级」和「距上次推送
   够久」。老客户隔半小时回来、说的是另一件事（上午交通事故 / 下午拖欠工资）、
   还留了另一个号码——档位没变、时间没到，于是**一条不推**。
   客服那边永远停在上一版：案由是错的、电话是作废的、摘要是上午那件事。
   **这不是防打扰，是丢单。** 已加 `lead.worth_renotifying`：弱→强、
   联系方式变了/刚拿到、分数涨了一截（≥15，意味着出现了新硬信号）——
   三者任一即再推一条，且前缀写明原因（客服才不会当成重复推送划走）。
   反向一律不推（分数会波动，「刚才急现在不急了」只消耗信任）。
   判据存在 `leads.notified_score` / `notified_contact`：只记 `notified_at`
   判不出「有没有新东西」。
2. **摘要跟着一起停摆。** `summarize=notify`，不推就不重算，于是控制台那张卡
   一直是上一通的内容。修好第 1 条即连带修复。
3. **联系方式取的是第一个号，不是最后一个。** 客户改口（「那个打不通，用这个」）
   时，交接单上抄的是作废的号码，而系统看起来一切正常。
   `signals.scan` 改为后者覆盖前者。

## 转接之后的三件事（2026-08-08 真机第三轮）

1. **改派必须把微信客服会话本身也搬过去。** 原来 `reassign_lead` 只改我们库里的
   `assigned_userid` 再给新律师推一张单，而企微那边的会话状态一动没动——
   新律师的「微信客服」工作台里根本看不到这个人，老律师那边倒还在。
   单子看着交接完了，客户实际上还挂在原来那个人名下。已加 `_move_kf_session`：
   只对**已在人工接待中**的会话搬（还在 AI 手上的没有归属，强搬只会让 AI 当场闭嘴）；
   先校验新律师是不是该客服账号的接待人，不是就明说，**绝不静默**。
2. **转过去没人露面，不能让客户对着空气说话。** 真机实测：客户被转人工后连发
   「你好」「人呢」「你好？」，AI 全程沉默，直到企微把会话判成「已结束聊天」。
   转接的本意是让他更快见到人，结果是被晾在一间空屋子里——**比不转还糟**。
   新增 `handoff_grace_seconds`（默认 90 秒）：过了宽限期 AI 接着陪
   （`handoff:no-show`），但**不清转接状态**，律师随时能接手，
   他一开口 `being_handled` 立刻又把 AI 按住。`handoff_reclaim_seconds` 保留为
   更晚的那一档，语义从「到点必响的闹钟」收窄为「彻底放弃等人」。
3. **律师要能移除。** 名下还有在办线索的不给删——删了那些线索的负责人就成了
   一个查无此人的 id，交接单推不出去、督办找不到人，而没有任何地方会说明原因。
   提示改派或改用「停用」。历史归属（线索上的 assigned_userid）刻意不动：
   那是发生过的事实，抹掉等于篡改台账。

## 会话归属在企微那边（2026-08-08，「转过一次人工就再也不回」的真因）

微信客服的会话有归属状态：0 未处理 / 1 智能助手 / 2 待接入池 / 3 人工 / 4 已结束。
**我们一直只会把它转给人工（`transfer` → 3），从来没有要回来过**——
`STATE_ROBOT` 定义了却一次没用。于是客户被转过一次人工、或者会话被企微判成
「已结束」之后，新消息进来是「未处理」，而**未处理的会话没有任何人在接，
客户发什么都石沉大海**。我们这边判断照常跑、回复照常入库、日志一切正常，
所以从代码里怎么看都看不出问题——**问题根本不在判断层，在企微那边的归属上**。

- `KfClient.to_robot()` → `service_state=1`，把会话要回给 AI。
- `worker._ensure_robot_state`：客户消息进来时，若我们认为该由 AI 接
  （未转人工，或转了但人不在跟），就查一次状态，不是 1 就要回来。
  **同一通会话十分钟只查一次**——这是每条客户消息都走的路径。
- 「收回给 AI」按钮同时清本地标记**和**改企微状态：只清本地是假动作。
- 控制台自检（`/console/diagnose`）把真实状态摆出来：0/2/4 直接判定为
  「没人在接」并给出修复动作。

教训：**跨系统的状态，本地那份永远只是影子。** 判断层再对，
只要归属不在自己手上，一个字也送不到客户眼前。

## 管理员视角（2026-08，律所方要求）

律所方原话：「我们这个平台都是给管理员用的」「管理员不想看到那么多 AI 对话，
那么乱」「看板应该是看当天的、当月的」「方便看得到员工的表现以及处理情况」。

底层判断：**控制台是给「在系统里干活的人」用的**——律师看自己的单、点已联系。
所主任要的是另一样东西：一份推到眼前的摘要，和一张能拿去开会的表。
指望他每天主动打开网页看数字，这件事不会持续超过一周。

据此四条：

1. **每日战报**（`responder/digest.py`，worker 按 `daily_digest_hour` 推）：
   只答三个问题——昨天进了多少人、多少是真线索、谁在跟跟上了没有。
   永远说**完整的昨天**（早九点推时「今天」才过九小时，跟昨天比没有意义）。
   零线索时要说清「没线索」与「通道断了」的区别，后者每多一天都是真钱。
2. **Excel 导出**（`responder/exporter.py`，`GET /console/export/leads`）：
   管理员的主视图。**AI 对话不进表**，只留一列深链。
   时间格式化成「08-06 15:47」——ISO 时间戳不是给人读的。
3. **看板按时间范围**（`resolve_range`，默认今天）：全时段累计只在开张第一天
   有意义，之后越来越像一个常数，看不出好坏也就没人再看。
4. **员工处理情况**（`Store.staff_performance`）：分到/已跟进/成交/**平均响应时长**。
   最后一项最要紧——线索价值随时间塌得极快，一小时内打过去和第二天打过去
   是两桩生意。未联系的 P0 单独标红：那是唯一需要管理员当场做点什么的数。

导航顺序即优先级：看板 → 线索 → 会话 → 团队 → 知识库 → **AI 质检**（原「记录」）。
把 AI 对话流摆在第三位，等于天天在请管理员去读它。


## 长期记忆（2026-08，落地中）

律所方要「越用越聪明」。**做法是检索，不是训练**：一年约 4700 通对话，
对微调差两三个数量级，对检索绰绰有余；而且检索能「改一条立刻生效」、
能说清依据出自哪一条——后者对律所是硬要求，答错了要追得到出处。

**第一层已落地：组织记忆 = 律所知识库**（`responder/memory.py` + `knowledge` 表）

- 检索用中文二元组 Dice 相似度暴力打分。**不上向量库**：几百到几千条的规模，
  全表算一遍是微秒级，向量库换来的是察觉不到的速度差，代价是多一处会挂的服务。
  超过约 5000 条再换不迟。
- **检索不到就什么都不注入**（`MIN_SCORE`）。塞一条不相关的知识比不塞更糟：
  模型会努力把它用上，于是答非所问，而且答得理直气壮。
- **只有 approved 会被引用**。知识库条目就是话术，须人工审核后才对客户生效
  （见合规护栏）。导入与机器提炼一律落 draft。
- 口径注入在客户问题**之前**，并显式声明「与边界冲突时以边界为准」——
  口径里若含金额，模型也不得复述。
- `hits` 记录每条被引用次数：用不上的条目该被清掉，而不是越攒越多。
- 知识库出任何问题都静默降级（`service._recall` 吞异常）——它是增强不是依赖。
- **审核台在控制台「知识库」页**（`tab-kb`）。没有它，导入就是个死胡同：
  条目落 draft，而 draft 永远不会被引用，于是导了等于没导。待审核数挂导航角标。
- 每条列出时带 `flagged`＝这条答案踩了哪些禁止事项，**且踩了就不许通过审核**
  （`set_knowledge_status`）。出口闸门当然还会拦，但那时的表现是 AI 的回答被
  整段丢掉换成兜底话术——客户看到一句答非所问的套话，而没有人知道原因出在
  知识库某一条上。抖音那批现成话术里「电话咨询免费」之类比比皆是，
  逐条人眼看是看不出来的。
- 改写条目一律退回 draft（`Store.update_knowledge`）：审核过的是那个旧答案。
- 两条导入路径，规矩相同（都落 draft）：控制台粘贴（`POST /knowledge/import`）
  给律所方自己用；`opscmd.import_knowledge` 读仓库里的 `ops/knowledge.tsv`，
  给「已经在仓库里筛好了合规、不该让人再粘一遍」的情况用。

**第二层已落地：客户记忆**（`groups.memory` + `memory.build_customer_memory`）

- **只由已入库事实拼装，不让模型写。** 模型写摘要更流畅，但它会补细节；
  记错一件客户没说过的事（「上次您说要离婚」——他没说过）比完全不记得更伤人，
  而且当场穿帮。只搬运确定的：上次何时来、什么案由、他说过的关键事实、进行到哪一步。
- **在会话静默后沉淀**（`worker._sweep_customer_memory`），不是每条消息都算：
  记忆是给下一次用的，聊到一半的事实往往还会被后面几句改写。每次覆盖重算，不做增量。
- **只在回访时注入**（`service._customer_memory`）：同一通对话里完整历史本就在上下文，
  再塞一遍会让模型把「上次」和「刚才」搞混。已委托客户不注入——律师全程在跟。
- `Store.set_memory` 独立于 `upsert_group`：记忆是后台异步写的，而建档更新高频，
  混在一起会被一次普通的建档随手覆盖成空。
- 定时扫描只回看 24 小时，**功能上线前就安静下来的会话落在窗口外**，
  由 `opscmd.backfill_memory` 补一次（那批恰恰是最早的客户，最可能回访）。

**待落地**：从律师实答中提炼知识库草稿条目。

**AI 能读律师接手后的对话**：转接后消息照常入库（`origin=5` → `sender_is_staff`），
AI 只是不发言。所以「律师实际怎么答」这份数据一直在攒，它是知识库最值钱的种子。
