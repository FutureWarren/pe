# 抖音企业号私信接入

> **⚠️ 现状（2026-08）：本通道已实现但"保留不启用"。**
> 抖音正在收回第三方应用的私信能力（见《线索类小程序私信能力回收通知》），
> 并把商家导向自家的免费产品「AI即用」（其文档明写"无需通过第三方开放平台"）。
> 抖音侧的接待改用 AI即用，配置见 **`docs/douyin-ai-setup.md`**；
> 线索仍通过客资中心导入我们系统。
> 本通道代码保留为退路：不配 `RESPONDER_DOUYIN_CLIENT_KEY` 即不激活。

## 为什么做这条通道

用户第一次接触律所的场景很反直觉：**不在微信，在抖音**。直播和主页私信是
first pass 的真实入口，微信客服要客户先扫码，多了一个动作，转化在那一步就掉了。

抖音后台实测漏斗（一周）：

| 环节 | 人数 | 转化 |
|---|---|---|
| 进私信 | 416 | — |
| 开口说话 | 90 | 21.6% |
| 留下联系方式 | 50 | 55.6% |

两个断点正好都是 AI 能补的：**进来没人说话**（进线问候）、
**聊完没人要电话**（收口话术）。这两件事在微信客服通道已经做完，
抖音通道复用同一套判断、话术、线索与合规链路，只是发送侧受平台限制。

## 平台硬限制（不是我们的策略，别往大了调）

| 限制 | 数值 | 代码位置 |
|---|---|---|
| 只能回复，不能主动发起 | 客户没开过口就发不出去 | `service._douyin_budget` |
| 回复窗口 | 客户最后一次发言起 24 小时 | `douyin_reply_window_seconds` |
| 窗口内条数上限 | 6 条（**分条后的真实条数**） | `douyin_max_parts_per_window` |
| 进入会话事件响应 | 30 秒内 | `worker._douyin_welcome`（确定性模板，不进模型） |
| 账号资格 | 认证企业号（蓝V）及其员工号 | — |

**为什么分条上限要单独收敛到 2 条**：微信侧一条回复拆 1~3 条更像真人打字，
但在抖音，3 条 × 2 轮就打满 6 条配额，之后真正要紧的话（要电话、邀约到所）
反而发不出去。`douyin_split_max_parts=2` 是为了把配额留给收口动作。

**为什么配额要按分条后的条数算**：平台数的是真实消息数。一行 `replies` 可能
对应 3 条真实消息，按行数算会低估一倍以上，等发现时配额已经打满。
故 `replies.parts` 记录实际发出条数，`Store.sent_parts_since` 按它求和，
且把 `mode='failed'`（发了一半失败）也计入 —— 前半截平台已经收下并计了数。

## 律所侧要做的（长杆，先做）

审核要几个工作日，代码这边随时就绪，所以这一步越早提交越好。

1. 打开 **open.douyin.com** → 右上角登录 → 选**自研开发者**
2. **企业认证**：用蓝V 抖音号扫码验证，企业信息会自动带出，不用手填
3. **创建应用**：类型选与「生活服务商家 / 企业号」相关的那一类
   （我们是本地生活服务商家，卖的是团购咨询）
4. **申请权限**（在应用的「权限管理」里逐个申请，都要过审）：
   - 接收私信消息
   - 发送私信消息
   - 用户进入私信会话页事件
5. 过审后在「凭证与基础信息」取 **client_key / client_secret**
6. 在「事件订阅 / 回调配置」里填回调地址：`https://<服务器地址>/douyin/callback`，
   并设一个**回调校验 Token**（随便一串，记下来）

把 client_key、client_secret、回调 Token 三样给我，我配上去即可。

## 上线自检

```bash
python scripts/douyin_smoke.py            # 验凭据
python scripts/douyin_smoke.py --probe    # 试探发送接口的正确路径
python scripts/douyin_smoke.py --to <open_id>   # 对测试账号发一条真消息
```

`--probe` 存在的原因：抖音文档站在部署环境不可达，发送接口的确切路径没法从
文档确认，所以 `RESPONDER_DOUYIN_SEND_URL` 做成了配置项。脚本会逐个试候选路径
并打印能通的那个，照着改一行 `.env` 就行 —— 不改代码、不重新部署。

## 会话主键

- 活的私信对话：`dyim:{open_id}`
- 导入的历史客资（客资中心导出的 xlsx）：`dy:{手机号}`

刻意分开两个命名空间：一个是活对话，一个是历史留资记录。同一个人两边都有时，
靠联系方式在线索层合并（`Store.find_lead_by_contact`），不靠主键撞车。

## 与微信客服的关系

判断层完全同构 —— 两者都是「客户主动找上门的一对一窗口」，因此
`GroupProfile.is_kf` 对抖音会话也返回 True：不等待、不对开场白沉默、
非文本消息转人工。差异只在「怎么把字发出去」，全部收在发送层。
