# 跑通「微信客服」这一条路 —— 上线手册

> 目标只有一个：**客户在微信里问一句，AI 当场答上，答不了的一条不漏地落到销售那儿。**
> 订单、库存、ERP 对接全都不是前提——没有它们，AI 照样能接住一大半售后问题，
> 剩下的转人工。**先让它活着，再让它聪明。**

---

## 〇、一条不让步的底线

「无论以什么方式」有一个例外，而且只有这一个：
**不引入任何个人微信的协议桥接 / 逆向 / 挂机方案**（iPad 协议、Hook、网页版逆向、
RPA 操作个人微信……）。理由不是洁癖：

- 微信对这类工具是**封号**处理，封的是号，不是软件——两万多个关注用户、
  客户的聊天记录、门店的客情，一起没。
- 它同时是《个人信息保护法》上的违法处理（未经同意收集客户对话）。
- 企微 2024-06 的公告点名过 RPA 自动化企业微信。

除此之外的任何官方通道都可以走。下面两条就是全部的官方通道。

---

## 一、两条路的现状

| | 企业微信「微信客服」 | 微信公众号（服务号） |
|---|---|---|
| 我们的代码 | 早就写好（律所在用） | 已写好并接通 |
| 全自动收发 | 可以 | 可以（认证服务号） |
| 现在能不能开 | **不能**——华为对经销商有管控 | 能，号已认证，20,557 关注 |
| 要不要引流 | 要（客户得先扫码进客服） | **不用**——那两万人已经在里面了 |
| 拦路的事 | 品牌方点头 | 这个号**已授权给云盛 ERP** |

**所以第一期走公众号。** 企微那条不是废弃，是等华为松口；两条路在我们这边
共用同一套判断、合规、留痕，换通道只换发送那一个对象。

## 二、消息推给了谁——已查明（2026-08-27，看过授权管理页）

先前担心的是：这个号已经授权给了第三方平台，微信会把消息推给它们而不是我们。
**这个担心被账号自己的现状否掉了。**

公众号后台「设置与开发 → 第三方平台授权管理」显示，两家平台**同时持有
「消息管理」**：

| 第三方平台 | 权限数 | 消息管理 | 网页服务 |
|---|---|---|---|
| 云盛久惠宝 | 22 | ✔ | ✔ |
| 会员云平台 V8 | 23 | ✔ | ✘ |

两个结论，而且互相印证：

1. **「消息管理」不互斥。** 两家同时拿着它，这不是推论，是现状。
   所以我们可以是第三家——**要的是「加一份」，不是「换一份」，不用解绑任何东西。**
2. **「网页服务」是互斥的那一集**，所以只有云盛有、会员云没有。
   一个非互斥的两家都有、一个互斥的只有一家，权限模型就是这样运作的。
   （我们不需要网页服务。）

### 客服消息不能单独拆出来，但那不重要

微信的最小授权粒度是「权限集」，而**发客服消息和接收用户消息同属
「消息管理」这一集**，没法只要其中一半。但这对我们没有影响，因为我们要的
正好是这一整集。

真正要紧的是**会员数据不在这一集里**，所以完全不会被牵动：

| 云盛靠什么吃饭 | 在哪一集 |
|---|---|
| 会员信息、用户列表 | 用户管理（②） |
| 商城/会员卡认人 | 网页服务（④，互斥，他们独占） |
| **订单通知（模板消息）** | **群发与通知（⑦）** |
| 底部菜单 | 自定义菜单管理（⑮） |

### 因此第一期很可能只是「填一个 URL」

微信开发社区对「授权了多个第三方平台之后，还能不能在基本配置里设自己的
服务器」的口径是：**能，一般不冲突，除非双方对同一事件都做被动回复。**

这一条来自社区问答而非官方文档明文，所以**当作待实测**，但验证成本接近零、
随时可撤（见第三节第 3 步）。

**而我们结构上没有那个冲突点**：`/mp/callback` 永远返回 `success`，
从不返回被动回复 XML——回复一律走客服消息接口异步发。所以即使三家同时收到
同一条消息，客户那头也只会有我们这一条。
（这个设计原本是为了躲开「5 秒超时会显示『该公众号提供的服务出现故障』」，
正好在这里派上用场。别把它改成被动回复。）

### 走不通时的两条备选（按代价排）

1. **让云盛转发**——他们的「久惠宝设置」里有「客服列表」，说明产品内建客服能力。
   一个电话的事，不动任何现有功能。
2. **我们自己注册成第三方平台并列授权**——微信开放平台认证 300 元 + 创建第三方
   平台走审核 + 一个备案域名，几天到两周。零解绑、零风险，只是慢。

**「取消云盛的授权」这条已经从方案里删掉了。** 既然不互斥，就没有理由动它；
而且真动了会坏掉他们的关注回复、关键词回复、菜单事件和那个客服列表。

### 开启服务器配置之前先看一眼

开启「服务器配置」（开发者模式）会让**公众号后台自带的「自动回复」失效**。
云盛已经持有消息管理，那套自带的多半早就没在用——但先打开
「设置与开发 → 自动回复」确认一眼，有内容就截图记下来，搬进话术表。

## 三、五步上线

每一步都有一条当场能验的命令。**不许跳过验证往下走**——
这条链路上每一步失败的样子都是「一切正常，就是没反应」。

### 第 1 步：把话术填上（不需要服务器，现在就能做）

```bash
python scripts/retail_demo.py --template 话术.csv   # 写出空表
python scripts/retail_demo.py --gaps                # 看还缺哪几条
```

出厂默认里**刻意留空三条**，因为它们各自是一句只有门店说了才算数的话：

- **门店位置与营业时间** —— 几家店、地址、几点到几点
- **正品行货质疑** —— 对外怎么说（涉及华为对经销商的口径，要拿到原文）
- **支付方式与开票方式** —— 收什么、能不能开专票

其余六条（保修/激活/数据迁移/分期/活动/选型）有默认值，**但也要过一遍**：
「进水算不算保修」「贴膜送不送」全国政策一样、各家做法不同，
照抄官方条款会当着客户的面跟门店的实际做法打架。

填完配 `RESPONDER_RETAIL_PHRASES_PATH`。**改一条立刻生效，不用重启。**

### 第 2 步：看它会怎么说

```bash
python scripts/retail_demo.py --phrases 话术.csv
```

走的是**线上同一条链路**，把「客户看到的」和「销售看到的」并排打出来。
（上一版的教训：演示工具骗了自己人，比没有演示工具更糟。）

### 第 3 步：服务器与凭据（顺便把第二节那条实测掉）

- 一台有**固定公网 IP**、能装 HTTPS 的机器（80/443 对外）。
- 公众号后台 → 设置与开发 → 基本配置：拿 AppID / AppSecret。
  **重置 AppSecret 之前先确认现有第三方对接**——这个号还挂着云盛，
  重置会把他们一起打断。
- 同一页的 **IP 白名单**：把这台服务器的公网 IP 加进去
  （那里已经有 10 个阿里云 IP，是云盛的，别删）。

```bash
python scripts/mp_preflight.py --url https://你的域名
```

第 ② 段拿到凭据就说明 AppSecret 和 IP 白名单都对了。

**然后把回调填进去实测**（半小时，随时可撤）：
基本配置 → 服务器配置 → 填 `https://你的域名/mp/callback` + Token → 提交。
微信当场发一个 GET 来验，通不过会直接报错——**不会影响云盛和会员云**。
提交成功后找个同事发一句「保修多久」，再跑一次自检看第 ④ 段计数有没有涨。

涨了 = 第二节那条成立，这条路通了，什么都不用解绑。
没涨 = 走第二节末尾那两条备选。把服务器配置删掉，两家平台一点感觉都没有。

> 凭据这里有一个已经处理掉的坑：`/cgi-bin/token` 是「谁最后取谁算数」，
> 两套系统轮流刷会互相顶掉，症状是两边间歇性报 40001、重试有时又好了，
> 看起来像网络抖动。我们走的是 `/cgi-bin/stable_token`，**不会顶掉别人的**。

### 第 3.5 步：待办要有出口（五分钟，别跳过）

企微里建一个群（销售 + 店长）→ 群设置 → 群机器人 → 添加 → 复制 Webhook，
配到 `RESPONDER_RETAIL_TODO_WEBHOOK`。同时配上 `RESPONDER_PUBLIC_BASE_URL`，
推送里才带得上「看完整对话」的链接。

**不配的后果不是「少个功能」**：AI 答不了的那些会落成一条运维小记——
查得到，但没有人会去查。客户问了一句，后台一切正常，而那边没有任何人知道。
**这是整条链路上最后一处静默失败。**

选群机器人是因为它不需要任何管理员审批（华为管控下企微能不动就不动）、
不需要 access_token（不跟别的系统抢凭据），而销售本来就在企微里。

响铃的规矩：**一次「叫人」只响一次**。客户连发三句补充时落库落三条（记录要全），
但只响第一次——响到第三次他就把这个群折叠了，而那正是最要紧的时候。
补充的内容通过那条链接看，不靠刷屏送达。

### 第 4 步：影子模式跑一周

```
RESPONDER_RETAIL_MODE=shadow
```

全流程照跑、回复照样入库，**就是不外发**。让一位同事关注这个号、发几句真实问题，
在控制台「AI 质检」里逐条看它会说什么。**先看它会说什么，再决定让不让它说。**

这一周同时验证第 ④ 段的计数在涨——只要在涨，第二节那个问题就已经解决了。

### 第 5 步：开真

```
RESPONDER_RETAIL_MODE=live
```

第一周只在非营业时段开（人少的时候本来就没人回，AI 只赚不亏），
稳了再全天。

## 四、上线之后天天要看的三个数

`/health` 和 `mp_preflight.py` 都能看到：

| 数 | 它变坏时的意思 |
|---|---|
| `retail_blocked` | **有回复没发出去，客户一个字没收到**——最贵的一种失败 |
| `retail_send_failed` | 接口失败，同上 |
| `retail_escalated` | 转人工的量。它一直涨说明话术缺口大，该补话术而不是加人 |

**那 5 条/窗口的客服消息额度是三家共享的**——云盛发模板消息也吃它。
代码里已经按共享算（`test_the_quota_is_shared_with_whatever_else_uses_this_account`），
所以 `retail_blocked` 涨起来时，先看是不是他们那边在群发。

还有两个跟待办有关的：`retail_todo_unrouted`（**没配 webhook**，
待办没有出口）、`retail_todo_push_failed`（推不出去）。
两者在客户那头长得一样，在后台也一样安静，所以分开数。

## 五、这条路上我们已经替你踩过的坑

都在 `tests/unit/test_retail_pipeline.py` 里守着，写在这儿是为了别有人「优化」掉：

1. **微信会重推**（最多三次，MsgId 相同）。不去重＝客户一句话被回三遍，
   那三遍还各吃掉一条 5 条额度里的份额。
2. **额度是这个号的，不是我们的。** 云盛和会员云也在用它，
   他们先发满，我们一条也发不出去。
   同理，**`/mp/callback` 必须永远返回 `success`、绝不返回被动回复 XML**——
   一个号上挂着三套系统，被动回复是唯一会让客户收到两条的地方。
3. **窗口要拿真实的此刻算**，不是拿消息自己的时间——否则 48 小时那道闸
   永远不会响，直到接口开始报 45015。
4. **转人工之后的三分钟属于那个人**：不重复回执，也不再自己接话。
   （客户说「我要退货」，十五秒后补「买了才三天，还没拆封」——那是同一件事的
   下半句，可意图识别是无状态的。再多的词表也修不掉，所以规则在时序上。）
5. **销售待办追加不覆盖。** 覆盖那一版：客户连问四件事，销售那边只剩最后一件，
   而待办**看起来是有的**。
6. **客户发语音/图片不能沉默**，也不能猜内容——给一句实话，连发四张只回一句。
7. **关注/菜单事件不由我们回**：公众号后台自己配了自动回复。
   一个窗口只该有一个人在说话。
