# 分案与优先级规则（强意愿的定义）

本文是 `engine/priority.py`（评分）与 `assignment.py`（派单）的业务定义，三者必须同步演进。
阈值与权重的任何调整属于「判断阈值」变更（见 CLAUDE.md），须人工确认后合并。

## 全流程闭环

```
客户咨询（微信客服 / 群 @ 助手）
   → AI 第一响应 + 首轮筛查（零等待）
   → 优先级评分（本文规则，纯规则可解释）
   → 自动派单（负载均衡：谁在办的最少谁先接）
   → 企微单聊推交接单给被派律师（含优先级与评分依据）
   → 律师用个人账号进工作台：只看自己的客户，照单打电话
   → 标记「已联系 / 已成交 / 无效」
   → P0 超时未联系 → 自动督办 + 抄送第二责任人
   → 看板按律师复盘转化漏斗
```

## 一、强意愿的定义（优先级评分）

每条线索按下表累计得分（上限 100），**每一分都指向对话里可核验的事实**，
推送与工作台都会展示依据清单（如「已留电话 +40 · 明确委托意向 +35」）：

| 信号 | 分值 | 判定方式 |
|---|---|---|
| 已留电话（手机/座机） | +40 | 正则提取，绝不经模型（抄错一位就打不通） |
| 明确委托意向（想委托/请你们接/签合同） | +35 | 关键词规则 |
| 想面谈/来所/预约 | +30 | 关键词规则 |
| 主动要律师电话 | +25 | 关键词规则 |
| 有人受伤 / 住院 | +25 | 关键词规则。不是普通的意向强弱——伤情鉴定、责任认定、医疗票据都有窗口，时间在往外流 |
| 要加微信详聊 | +20 | 关键词规则 |
| 问到收费 | +15 | 关键词规则 |
| 紧急情形（拘留/传唤/开庭临近等） | +25 | 判断引擎紧急规则，同时**直接置顶** |
| 涉及金额 ≥10 万 | +10（≥1 万 +5） | 只认「X万/X元」带单位写法，防手机号误伤 |
| 有时限压力（开庭/时效/截止将近） | +10 | 关键词规则 |
| 客户明确表示很急 | +10 | 关键词规则。单独不足以定档（谁都会说急），但配上受伤或留电话就是压垮骆驼的那一根 |
| 沟通深入（客户 ≥6 条消息） | +5 | 会话统计 |

评分只统计**本次咨询**（同一客户隔 2 小时以上再来算新一次，`lead.current_session`）。

### 分层与响应时限（SLA）

| 层级 | 门槛 | 含义 | 要求 |
|---|---|---|---|
| **P0 强意愿** | ≥60 分，或紧急情形 | 可行动（有联系方式/明确意向）且强烈 | **1 小时内联系**；超时自动督办并抄送第二责任人 |
| **P1 有意愿** | ≥30 分 | 有一项强信号（如留了电话但意向未聊透） | 当天联系 |
| **P2 一般** | <30 分 | 普通咨询 | 48 小时内跟进或仅归档 |

典型组合：留电话+想委托 = 75 → P0；只留电话 = 40 → P1；只问收费 = 15 → P2；
被拘留（紧急）→ 无条件 P0。

- 门槛在配置里：`priority_p0_threshold=60`、`priority_p1_threshold=30`。
- **分数只决定排序，不决定转不转人工**（2026-08-09 律所方拍板）。
  「现在要不要把真人叫过来」由 `priority.WANTS_HUMAN` 那张清单回答，
  与分数完全解耦——见 `docs/kf-handoff.md`「什么时候转」。
  两件事绑在一起过一阵子，代价是客户说了「让律师给我打电话」而系统
  还在算他够不够 60 分。
- 督办参数：`lead_p0_sla_seconds=3600`，每单只追一次，避免变成骚扰。
- **督办的前置条件**：线索已通知或已指派（计时起点取两者中先发生的那个），
  且系统处于 live 模式。影子模式不外发任何消息，自然也不督办。
- **试点第一周结束后用真实数据校准一次权重与门槛**（对照：律师实际回电顺序
  与评分排序的偏差样本），校准结论须人工确认。

### 通知节流（与评分正交）

评分决定**排序**，通知与否仍按意向档位节流：hot/warm 首次达到或升级时推送一次，
cold 只归档不打扰（`lead.should_notify`）。也就是说 P2 线索照样入库可查，
但不会半夜给律师弹消息。

## 二、派单规则（谁接这单）

按顺序命中即停：

1. **粘性**：该客户已派过且律师在职 → 不换人。客户二次进线换人接待，
   背景全部作废，是体验事故不是负载均衡。
2. **跨渠道认人**：同一手机号在别的通道已有承办律师 → 沿用他。客户先在抖音留号、
   后扫码进微信客服，是同一个人，不能两位律师各打一遍。
3. **负载均衡**：在办线索（new + contacted）最少者优先；平局时最久没接单的先接。
4. **名册为空 = 未启用**：回落旧链路（客服接待人 → 全局兜底），升级部署零配置不炸。

**不看专长**（2026-08-12 律所方定：「客服不分什么专长不专长」）。原先还有一层
「案件类型 ⊇ 律师专长领域」，已整层删除——律所的实际组织是接单的人就是客服，
谁有空谁接，案子定下来再由所里内部分。多一个匹配维度只多一类静默失败：
专长填错就一直派错人，而且没人看得出来。

派单同时回写会话档案的承办律师：后续紧急提醒、话术点名（「我帮您叫X律师」）、
人工接管判定全部跟着换人。管理员可在工作台手动改派，改派即时通知新负责人。

停诊/休假：把律师的「接单」开关关掉即不再进入派单池，手上已派的单不受影响。

## 三、律师账号与数据边界

- 每位律师一个个人登录链接（管理员在「团队」里签发，可直接企微发到律师本人）。
  令牌只存哈希；链接放在 `#` 片段里，服务器与 nginx 日志都不落令牌。
- 律师身份看到的待办/线索/记录/看板/会话，服务端一律只返回**派给自己**的部分；
  管理员令牌看全量并多一张分律师负载表。
- 律师可以给自己的会话关 AI、标记线索状态；改派、群档案编辑、模式切换、
  发版等管理操作仅管理员可用。
- 令牌每次重发即轮换，旧链接立即失效；离职即停用（`active=0`），历史归属保留。

## 四、案例走查

> 客户：我们公司拖欠了我三个月工资，一共4万多，昨天把我辞了
> 客户：这种能仲裁吗？大概怎么走流程
> AI：（解答 + 引导）
> 客户：我想尽快处理，你们能接吗？电话17721275495，微信同号

评分：留电话 +40，明确委托 +35，金额 4 万 +5，要加微信 +20 → 100 → **P0 强意愿**。
派单：不看案由 → 在班客服里在办最少的一位（都一样多时，最久没接单的先接）。
推送：交接单首行「【P0 强意愿】劳动仲裁 · 较急 · 建议 1 小时内联系」+ 依据清单。
若 1 小时后该单仍是「新线索」：督办提醒律师本人 + 抄送第二责任人。


## P0 门槛只管「转接」，不管「服务」（2026-08）

律所方问：只按 P0 转接，会不会把 P1 丢掉？不会，但当时确实有一个真实缺口。

**每一档都派单、都推交接单**（`lead.dispatch` → `assignment.ensure` → 企微私信），
只要意向不是 cold。P0 多出来的**只是转接**——把会话本身交到律师手上。
门槛卡在 P0，是因为转接会占住律师的即时注意力：一周 416 人进私信，
全转过去律师什么也别干了。

**评分是动态的，不是一次定终身。** P1 客户后来留了电话（+40）或说要委托（+35），
当场变 P0 → 自动触发转接。所以「P1」不是判决，是「还没到那一步」。

**当时真正的缺口：督办只扫 P0。** P1 单子推出去之后律师不跟，就再没有任何机制
会提起它——而 P1 恰恰是最需要有人推一把的那批（有意愿、还没留电话）。
已补：`lead_p1_sla_seconds` 默认 24 小时（P0 是 1 小时），
`Store.overdue_leads` 按档扫，0 可关闭。

| 档 | 派单 | 交接单 | 转接 | 督办时限 |
|---|---|---|---|---|
| P0 | ✅ | ✅ | 看清单，不看档 | 1 小时 |
| P1 | ✅ | ✅ | 看清单，不看档 | 24 小时 |
| P2 | ✅ | ✅ | 看清单，不看档 | 无 |
| cold | 仅归档 | 静默期后补一份 | 看清单，不看档 | 无 |

> ⚠️ **「转接」这一列不再看分档**（2026-08-09 律所方拍板，见下一节）。
> 表里保留这一列只是为了说明这件事——**别再把分数门槛装回去**。
> 判据是 `priority.WANTS_HUMAN` 那张清单：说要委托 / 想来面谈 / 要律师联系他 /
> 有人受伤 / 要加微信 / 留了电话 / 问到收费 / 问所址——任一即转。
> 装回分数门槛的代价律所已经付过一次：只问收费、只说想来面谈、只问所址的客户
> 从此不再转人工，而这三类恰是律所点名要求「直接转人工」的。


## 全量推送（2026-08，律所方决定）

律所方原话：「我们有很多的客服，所以只用标记好是强意愿还是弱意愿就好了。
全部都得推给客服，不能躺死在对话里。」

**这是前提变了，不是标准变了。** 原口径只推有意向的、冷线索仅归档，
成立的前提是接单的人手紧张——多推一条就是多占一次注意力。律所侧不是这个
前提，那条节流就从「保护」变成了「丢单」。

- `notify_all_leads`（默认开）：冷线索也推。
- **只放开门槛，不放开频次**：一通对话仍然只推一张单。
- 冷线索在**会话静默后**才推（`worker._sweep_idle_leads`），不当场推——
  客户刚说一句「在吗」时那张单上什么也没有，三十秒后他讲完案情还得再推一张。
- 推给客服的那张单只标 **强意愿 / 弱意愿**（`priority.bucket`）。
  P0/P1/P2 三档留在内部（评分、督办时限、看板还要用），但接单的人
  只需要回答一个问题：这单现在打还是排队打。分得越细，他越要停下来想
  「P1 和 P2 差在哪」——那一停就是摩擦。
