# 会话转接：不搬信息，搬客户

## 要解决的问题

现在的交接链路，最后一步是最脆的：

```
AI 跟客户聊 → 整理交接单 → 推给律师 → 律师打电话 → ❌ 客户没接
```

陌生号码接通率本来就低，何况我们的客户往往正在上班、开庭、或者正因为
被辞退而不敢接不认识的电话。前面攒的全部上下文，在「挂断」那一刻归零。

**会话转接换一个模型：AI 是前台，聊到该人接手时把人领进来，而不是把笔记递出去。**

```
AI 跟客户聊 → 判定值得人工接手 → 把会话转给律师 → 律师在原窗口接着聊
```

- **客户**：没有切换感，还是那个窗口，只是回话的人变了，不用等电话
- **律师**：打开企微就看到完整聊天记录，不用读交接单、不用自我介绍
- **我们**：「搬运」这个环节直接消失

## 机制

微信客服的会话有状态机，`kf/service_state/trans` 可以改：

| 状态 | 含义 | 我们的用法 |
|---|---|---|
| 0 | 未处理 | 新会话 |
| 1 | 由智能助手接待 | **AI 工作时的常态** |
| 2 | 待接入池 | 不用 |
| 3 | 由人工接待 | **转接目标**，需指定 `servicer_userid` |
| 4 | 已结束 | 会话收尾 |

转成 3 并指定律师的 userid，这通会话就出现在那位律师企业微信的客服工作台里，
历史消息齐全，他直接回就行。

> ⚠️ 接口名与字段以企微文档为准。开发环境访问不到 developer.work.weixin.qq.com
> （出网 403），故先跑 `scripts/kf_probe.py` 拿真实返回确认，再落地代码。

## 什么时候转（最关键的决策）

**转早了律所会被淹**：一周 416 人进私信，全转过去律师什么也别干了。
**转晚了就失去了那个当口**。

**判据是一张清单，不是分数**（律所方 2026-08-09 拍板，`priority.WANTS_HUMAN`；
2026-08-13 应转尽转后清单收底）：

| 客户做了什么 | 动作 |
|---|---|
| **紧急**（拘留 / 传唤 / 开庭临近 / 情绪崩溃） | **立刻转**，他还没开口要人，但等他开口就晚了 |
| 说要委托 / 要找律师 | **转** |
| 想来所里面谈 | **转** |
| 要律师直接联系他 | **转** |
| 有人受伤 / 住院 | **转** |
| 要加微信详聊 | **转** |
| 留了电话 | **转** |
| 问收费 / 问所址 | **转**（律所方 2026-08-10：问价的人在比较，要听到真人） |
| **把自己的情况说出来了**（substance） | **转**（应转尽转，2026-08-13） |
| 只打了个招呼，什么都还没说 | 不转。AI 先把情况问出来——下一句就够了 |

应转尽转是律所方 2026-08-13 的原话拍板：「但凡客户提供了他们的任何信息，
或者客户体现出了任何的意愿，我们都把他们转接到人工客服。」`substance` 信号
只由 service 在一对一进线窗口注入（`detect()` 不发它——没有渠道上下文，
群聊里每条实质消息都判热会搅乱群线索推送）。

原来这里挂的是「P0（≥60 分）才转」。**那是把两个问题绑在了一起**：
分数回答的是「十个人同时进来先给谁打电话」——排队问题，需要排序；
「现在要不要把真人叫过来」只需要知道客户是不是已经在要真人了。
绑在一起的后果，律所方在真机里撞见了：客户明明说了「让律师给我打电话」，
系统还在算他够不够 60 分，于是判成弱意愿、不转。

那道门槛当初是怕转太多（一周 416 人进私信）。**这个顾虑现在不成立了**：
转接后 AI 全程接着陪（不清转接状态，律师随时能开口接手，见下节）。
转多了的代价只是企微里多几个待接窗口，不再是客户被晾着——
代价变了，规则就该跟着变。

转给谁不用另做逻辑 —— `assignment.ensure()` 已经按在办量算出来了，
转接只是把那个决定**兑现**。

## 转接前要先跟客户说一句

直接转会出现一段尴尬的静默（律师还没看到）。所以顺序是：

1. AI 先发一句过渡话术
2. 再调 `service_state/trans`

```
您的情况我整理好转给律师了，他看到就在这儿回您。
趁这会儿咱们把情况再补全一点，材料（合同、聊天记录）也可以先发我。
```

> **不点名**（业务决策 2026-08，见 CLAUDE.md 对客称呼一条）。曾经考虑过点名——
> 转接这一刻人已经定了，说出来是准的。但律所方的判断更稳：客户读到名字就会等
> 那个人，而律师可能临时改派、可能没接手，等的就成了一个不会出现的人。
> 「有个具体的人接手了」这份分量靠**律师真的开口**来给，不靠一个名字。
>
> 末句给一个此刻就能做的事。转接不是终点——客户手上闲着的这段等待期最容易走神，
> 让他去翻合同、找工资条，既填住了等待，材料也真的有用。

## 转接之后：AI 接着陪，直到真人开口

**转接 ≠ AI 闭嘴**（2026-08-13，应转尽转的另一半）。转接的含义是
「让这个客户出现在律师的工作台里」；应转尽转之下几乎每个客户都会被转，
转完就静默的话，「被晾着」会成为每个客户的必经之路——旧版真机里
客户连发「你好」「人呢」全程无声，就是这么来的。

- `groups.handoff_userid` / `handoff_at` → 判断层记 `handoff:accompanying`，
  **AI 照常回复**：接着陪、接着把案情问全，材料照收
- 律师在窗口里说了一句（接管窗口内，`being_handled`）→ AI 让位
  （`gate:handed-off`）；他隔太久没再说话，AI 又会接上——判据是
  「最近说过」而不是「说过」，否则律师接手说一句，第二天 AI 还哑着
- 超过 `handoff_reclaim_seconds` 律师一直没开口 → 清转接记录
  （`_release_stale_handoff`），客户之后再表达意愿还能重新转
- `worker._ensure_robot_state` 对已转接的会话**一律不碰归属**——
  律师打开工作台时那通对话必须还在他名下

## 新增的失败模式（必须兜住）

转接不是成功的保证，它引入了一个**比现状更糟**的可能：
客户被交给一个不看企业微信的律师，晾在那儿没人理 —— 那还不如 AI 一直陪着。

三层兜底：

1. **转接后 SLA**：转接后客户又发了消息、而律师 N 分钟内没回
   → 提醒律师，再超时抄送第二责任人（复用 `notify/escalation.py` 的升级链）
2. **AI 全程接着陪**（2026-08-13 起）：真人开口之前客户始终有人应，
   「对着空气说话」这个失败模式整个消失；律师彻底没露面时到点清转接记录，
   之后还能重新转
3. **转接失败即回落**：`trans` 调用失败一律回落到现有链路
   （交接单 DM + 电话），绝不让客户悬着

## 律所要维护的名单只有两份（2026-08-12）

律所方问：「我们应该只有两个名单，为什么现在有三个名单？」——问得对，
第三份从来就不该由人来维护。现在的划分是：

| # | 名单 | 在哪里改 | 谁维护 |
|---|---|---|---|
| 1 | **律师名册**（＝客服名单，律师就是客服） | 控制台「团队」页 | 律所 |
| 2 | **升级服务的成员范围**（推名片用） | 企微后台 → 微信客服 → 升级服务 | 律所 |
| — | 客服账号的**接待人** | 由程序自动同步 | 不用管 |

第三份的正确内容永远等于第一份，所以由 `responder/kfroster.py` 保持一致：
名册一改就同步（`Store.upsert_lawyer` / `delete_lawyer` 打脏标记），
另外每 `RESPONDER_KF_SERVICER_SYNC_SECONDS`（默认 900 秒）兜一次底——
有人在企微后台手工删过接待人这种漂移没有任何征兆，只有下一次转接失败时才暴露。

> 为什么不在保存律师时同步调企微：企微接口会超时，那会让「加一位律师」这种
> 基本操作跟着失败，而名册其实已经存好了。所以保存只打标记，同步交给后台线程。
> 慢几秒没有代价，保存失败有。

第二份我们只能读不能写（`kf/customer/get_upgrade_service_config`），
所以它是唯一还需要人去企微后台点的东西。律所现在配的是「邀约谈案部」整个部门——
**部门里有谁企微不让我们读**，因此自检对它只提醒不判红：读不到就一个字都不下结论，
否则会把整份名册误报成没配好，而「说错坏了」和漏报一样贵。

## 最容易踩的坑

**律师必须是该客服账号的「接待人」**，否则 `trans` 直接失败——
上面那套自动同步就是为这件事做的。同步之外还有两道防线：

- `/console/kf/handoff-probe`（控制台「状态」页按钮「检查两份名单是否一致」）报四件事：
  **两份名单各自的内容与差集**（缺谁点名报出来）、接待人上次同步的时间与结果、
  开关与运行模式、以及**拿一通真实会话读一次 `service_state`**——只读不改，
  用来验证接口路径配得对。做成网页按钮而不是命令行脚本，是因为企微 API 限可信 IP、
  只有服务器调得通，而律所侧没有 SSH。
- 转接前再校验一次接待人，不在列表里的直接走回落链路，不做无谓的调用，
  **也不会先跟客户说「转给律师了」**——那句话发出去客户就真的在等了。

## 抖音那边

没有对等能力，也不需要 —— 抖音侧接待走 AI即用，它自带转人工
（负向情绪识别 / 关键词二次命中 / 命中转人工知识，见 `docs/douyin-ai-setup.md`）。
本方案是**微信客服专属**。

## 上线前的人工事项

1. **在企微后台把人配进「升级服务」**（名单二）：企微管理后台 → 客户与上下游 →
   微信客服 → 升级服务 → 服务专员范围。配部门（如「邀约谈案部」）或配具体成员都行，
   只要名册里的人都在里面。**这一份我们的应用没有写权限，只能人点。**
2. **点一次控制台的「检查两份名单是否一致」**，看到「两份名单一致、接口通」才算真的能用。

接待人那一份不用管了——名册一改，后台线程自己会同步过去（见上一节）。
控制台还留着一个「立即同步接待人」按钮，那只是「我不想等」，平时不用点。

> ⚠️ **不要去 kf.weixin.qq.com 手工点接待人**。这个客服账号由企微应用托管，那个后台
> 顶部横幅写着「正在通过企业微信应用管理相关能力，启用后将由此处统一接管
> 用户咨询和客服账号」——点了那个「开始使用」，管理权会被夺回网页侧，
> 消息推送会断，整套 AI 当场哑掉。既然程序有权限，就让程序加。

## 说到底这是个组织问题，不只是技术问题

转接能不能成，取决于**律师是否真的会看企业微信的客服工作台**。
技术上把客户送到门口很容易，人不开门就没用。

所以上线前建议先小范围试：**指定一两位律师做接待人**，跑一周看首响时长，
再决定要不要全所铺开。数据在控制台看板上（阶段 5）。
